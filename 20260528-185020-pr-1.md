## Executive Summary

PR #1 fixes a cross-process deadlock in the transfer service: the client-side credential responder now answers every `AuthRequest` with exactly one `AuthResponse`, falling back to `AuthType_NONE` when resolution fails, so the daemon's `GetCredentials` no longer blocks in `Recv()` forever. All three reviewers found the fix correct, minimal, and behaviorally equivalent to the existing anonymous-pull path. No critical or important issues surfaced; the four suggestions all strengthen test coverage.

All three agents independently confirmed the `NONE` fallback reuses the server-side anonymous path, and verified the fix against the included regression test (it times out on unpatched code and passes with the fix).

## Suggestions

S1. **Assert the anonymous fallback, not just liveness** — `core/transfer/registry/registry_deadlock_test.go:107-116` [Codex GPT 5.5]

```go
done := make(chan error, 1)
go func() {
	_, err := cc.GetCredentials(ctx, "docker.io/library/test", "registry-1.docker.io")
	done <- err
}()
```

The test discards the returned credentials and accepts any return — including an error or a non-`NONE` response. It proves the deadlock is gone but not the PR's stated behavior: a helper error should yield empty credentials and an anonymous pull. A future change that closed the stream on helper failure would still pass this test.

Fix: capture both return values, then assert no error and empty `Credentials`.

```go
creds, err := cc.GetCredentials(ctx, ref, host)
// assert err == nil && creds.Username == "" && creds.Secret == "" && creds.Header == ""
```

S2. **Cover the unmarshal-failure path** — `core/transfer/registry/registry.go:276` [Gemini 3.1 Pro, Codex GPT 5.5]

The test exercises only the `GetCredentials` error path. The unmarshal-error branch at line 276 also newly sends `NONE` instead of `continue`, but no test drives a malformed `AuthRequest` through it. Risk is low (it shares the fall-through), yet it is a distinct path the PR changed.

Fix: add a subtest that sends a corrupted or type-mismatched `typeurl.Any` on the client stream and asserts the server receives a `NONE` response rather than timing out.

S3. **`pipeStream.Close()` does not unblock the peer** — `core/transfer/registry/registry_deadlock_test.go:59-62` [Gemini 3.1 Pro]

```go
func (s *pipeStream) Close() error {
	s.once.Do(func() { close(s.closed) })
	return nil
}
```

Each endpoint owns a separate `closed` channel (lines 68-69), so closing one side leaves the peer's `Recv()` blocked — unlike a real gRPC/ttrpc stream, where `Close()` unblocks the peer with `io.EOF`. The current test never hits the product code's `stream.Close()` branch, so this is latent, but a future test of that path would hang.

Fix: share one `closed` channel and a `*sync.Once` between the paired streams in `newStreamPipe`, so closing either endpoint tears down both.

S4. **No test proves the stream stays usable after a failed request** — `core/transfer/registry/registry.go:278-290` [Claude Opus 4.8]

The PR chose `NONE` over closing the stream (alternative b) specifically because the bidi stream is reused for every credential request in a transfer; closing it would break later hosts. No test sends a second `AuthRequest` after a failed one to confirm the stream survives. This is the load-bearing justification for the chosen design, and it is the one behavior left unverified.

Fix: extend the test to issue a second `GetCredentials` call on the same stream after the helper-error request and assert it also returns.

## Review Process Notes

**Skill improvements**

- Add to the Testing dimension: when a test introduces an in-memory fake for a bidirectional or streaming interface (gRPC stream, socket pair, pipe), verify the fake's `Close()`/shutdown models the real implementation's teardown semantics — closing one endpoint should unblock the peer's blocked `Recv()`/`Read()`. A fake whose endpoints own independent close state can pass a deadlock-regression test while masking the very deadlock the real type would surface on the close path. Recognize it when a fake's `Close()` signals only its own endpoint.

- Add to the Testing dimension: when a PR's design rationale rests on a specific runtime property — a resource is reused across calls, a connection is shared, an operation is idempotent — check whether any test exercises that property. The justification for choosing one approach over an alternative is often the one behavior left unverified, because the author treats it as self-evident.

S1. **`pipeStream` mock implementation does not simulate bidirectional teardown** — `core/transfer/registry/registry_deadlock_test.go:59-62` (suggestion, gap)

The test's in-memory stream mock closes only the local endpoint's `closed` channel, leaving the peer's `Recv()` blocked:

```go
func (s *pipeStream) Close() error {
	s.once.Do(func() { close(s.closed) })
	return nil
}
```

In standard stream implementations (gRPC/ttrpc), calling `Close()` tears down the bidirectional stream and unblocks the peer with `io.EOF` or an error. If a future test exercises the client-side `stream.Close()` error path, the server would remain deadlocked.

Fix: Share the `closed` channel and `sync.Once` between the client and server streams, so closing one side tears down both:

```diff
 type pipeStream struct {
 	sendCh chan typeurl.Any
 	recvCh chan typeurl.Any
 	closed chan struct{}
-	once   sync.Once
+	once   *sync.Once
 }
 
 func (s *pipeStream) Close() error {
 	s.once.Do(func() { close(s.closed) })
 	return nil
 }
 
 // newStreamPipe returns two connected in-memory streams.
 func newStreamPipe() (client, server *pipeStream) {
 	c2s := make(chan typeurl.Any)
 	s2c := make(chan typeurl.Any)
-	client = &pipeStream{sendCh: c2s, recvCh: s2c, closed: make(chan struct{})}
-	server = &pipeStream{sendCh: s2c, recvCh: c2s, closed: make(chan struct{})}
+	closed := make(chan struct{})
+	once := &sync.Once{}
+	client = &pipeStream{sendCh: c2s, recvCh: s2c, closed: closed, once: once}
+	server = &pipeStream{sendCh: s2c, recvCh: c2s, closed: closed, once: once}
 	return client, server
 }
```
